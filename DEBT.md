# Engineering debt

Notes for the next engineer who touches this. Each item names what is wrong, when it bites, and what fixing it would cost.

## Domain debt

**The five-hundred threshold is per order, and that is the wrong scope.** `R_THRESHOLD` sums refunds for one order, so a customer with ten orders can be refunded €499 on each and never meet a human. The correct rule is per customer over a rolling window, and possibly per agent per day. The order was chosen as the scope because that is where the fold naturally lives, but the dangerous unit is the sequence, and this sequence boundary is too narrow. Fixing it is a `CustomerSummary` field and one more check; it should be the first priority.

**No periodic approval-expiry sweeper.** Stale `pending_approval` rows are reaped when ordinary traffic touches the customer: inbound mail (`post_inbound_email`), agent-loop resume (`run_agent_loop`), or operator approve/reject. A silent customer with no operator keeps a due approval indefinitely. Production should run a cron job or outbox worker that calls `expire_due_refunds_for_customer` for customers with active pending rows and resumes any returned open cases.

**The operator approves blind.** `GET /operator/pending` shows a refund id, an order, and an amount — not why the agent proposed it, what the customer wrote, or what the case has done so far. A human asked to approve a number with no context is a rubber stamp, which means the approval gate produces the appearance of oversight rather than oversight. The fix is to render the case event log and the customer's message on the approval view — cheap, and it changes what the control is worth.

**Nothing records why a refund was proposed.** The event log captures every decision the system made and none of the reasoning behind the proposal. When a refund is disputed later there is no answer to "why did it think this was justified". Model text is deliberately kept out of control state, but there is a middle ground not yet built: storing the model's stated rationale as evidence, clearly marked as untrusted and never read by a rule.

**A refund is the only thing this agent can do.** No partial refund reasoning, no replacement, no store credit, no "explain the return policy and close". Real support resolves most cases without moving money, and an agent whose only lever is a refund will reach for it.

**The reply text is not governed at all.** The gate decides whether a message goes out and to whom; it has no opinion on what it says. A model steered by a hostile email can promise a refund that will never happen, admit fault on the company's behalf, or invent a policy — all through a legitimate `send_reply`. This is the largest hole in the design and it is structural: the enforcement boundary is about actions, and this is about content. Templated bodies for anything with financial or legal meaning would cover most of it.

**Escalation is a dead end for the customer.** `escalate` closes the case and files a ticket. If the agent did not send a reply first, the customer hears nothing at all. Escalation should force an acknowledgement.

**Every email opens a new case, so the agent has no memory of the conversation.** A customer replying to our own reply gets a fresh case and an agent that has forgotten everything. Refund history is unaffected because it lives on the order, but the experience is bad and the model will re-ask questions it already answered. Threading is the fix and it is not small: it needs a reply-to correlation and a rule for when a case reopens.

**Verification is a bearer token with no binding.** Anyone who obtains the token can verify the customer. There is no rate limiting on the confirm endpoint, no entropy requirement, and the token sits in plaintext in the event log. It is a stand-in for a real out-of-band factor, not one.

**Identity rests entirely on the envelope sender.** No SPF, DKIM, or DMARC. Spoofing the sender grants everything the customer has, and `verified` only partly compensates because in this build it can be obtained through the same channel.

**Labels are static.** Classification is trivially correct here because every action type has a fixed set of labels, including `INTERNAL_SIDE_EFFECT` for `escalate` (a test/documentation invariant — policy obligations are table-driven and label-independent; no runtime reader exists). In anything real the labels depend on the payload, and whoever assigns them becomes the most valuable thing to attack — nothing here protects that. The gate still mediates ticket creation, but the policy cannot express a cross-case, per-customer, or time-window limit for it; the step cap only limits one case.

**Future adapter imports are statically scanned, not runtime-enforced.** The recursive AST scanner in `tests/invariants/adapter_import_scanner.py` (exercised by `test_every_non_gate_production_module_is_scanned_for_adapter_imports`) is the exhaustive static repository proof for discovered non-gate modules and direct or aliased adapter imports. Import-linter contracts are useful layering hygiene but are explicitly non-exhaustive at the package-root overlap; neither static check is a security boundary or substitutes for process/capability enforcement. Gate effect helpers require a spent `Authorisation` minted only by `policy.authorise` after a full `Allow` (rung 5 — constructible in-process, catches accidents); `RequireApproval` and `ForceEscalate` remain distinct verdict paths.

**Model worker egress is not OS-enforced here.** The shipped heuristic worker makes no outbound network calls, and the subprocess strips application packages from `sys.path`, but this repository does not install a deployment-level egress filter for a future remote LLM provider. A production backend that calls an external model API needs an explicit network policy at deploy time; until then the honest claim is: `ModelGateway` construction and transport selection are trusted Python; only serialized provider response bytes are untrusted input at the boundary.

**The model boundary closes the case; infrastructure failures do not.** `invoke_model_boundary` catches gateway exceptions and timeouts inside `MODEL_CALL_TIMEOUT_SECONDS`, validates exact-runtime `str` results, parses, and escalates with a fixed reason that carries no model text. Database errors, adapter failures, and other exceptions from `execute_agent_action` still propagate: swallowing them and closing the case would hide operational breakage. The honest split — model-boundary failures terminate; infrastructure failures leave the case resumable — is the right trade at this scale, but it means a payment crash or a missing label mapping still abandons the case mid-flight until someone replays or fixes the root cause.

**Named request and prompt limits trade audit fidelity for bounded storage.** `config.py` caps HTTP identity/content fields, action free text, raw model response bytes, invalid-output preview size, per-field prompt content, authorized order count, and total prompt UTF-8 bytes. Oversized HTTP fields return `422` before writes; oversized model responses close the case with a bounded audit digest rather than persisting the full payload; prompt envelopes that exceed authorized order count or total bytes fail closed before gateway use. The tradeoff is deliberate: attackers cannot force proportional database growth, but legitimate very large histories may hit caps and terminate or elide records.

**Mailer and ticketing effects are not atomic with their audit events (effect-first crash window).** The mocked adapter is called first and the success event is appended second. If the process dies in between, the customer can receive a reply with no `reply_sent`, receive a verification token the system cannot confirm, or a human ticket can exist with no `escalated` event. Retrying can duplicate the reply, send a replacement token, or create an orphan ticket. The real fix is a transactional outbox or an adapter-side idempotency and reconciliation protocol. The effect-first order was kept because it keeps the artifact small and makes the event mean that the adapter actually returned successfully; it is not a safe ordering.

**Money can move without a record.** The payment call happens after the transaction commits, so a crash in between leaves a refund marked `approved`, money gone, and no `refund_executed`. It is recoverable — `refund_id` is the payment idempotency key — but the reconciliation pass is not written, so today it is silent until someone reads the two systems side by side.

**The audit log is also the leak.** It stores raw email bodies, outgoing reply text, and verification tokens: exactly the material it exists to protect, with no redaction, retention limit, or access control.

**Append-only seeds, events, and refund intent have layered but incomplete guarantees.** `ImmutableRowError` blocks ORM updates/deletes on seed rows and events. Refund authorization intent fields (`id`, `customer_id`, `order_id`, `case_id`, `amount`, `created_at`) are ORM-immutable; status changes go through guarded SQL in `refund_transitions.py`. Composite ownership keys and composite foreign keys on events/refunds reject many cross-customer rows at the database when foreign keys are enforced (`relational_scope.py` validates before append). Raw SQL, another process, a DBA, or a migration can still bypass ORM listeners. **`events.case_id` tamper to another same-customer case is not rejected at append time** — it still relies on approval-time `validate_refund_intent_against_proposed_evidence` integrity checks rather than an append-time relational failure.

## Infrastructure

Projections are replayed in full on every action and will need an incremental version for long-lived customers. Single-flight is one in-process lock per case and breaks with more than one worker.

The default functional suite runs on SQLite, which serialises all writes, so the partial unique index, the customer row lock, and the transaction ordering are never genuinely contended there. **PostgreSQL 16.4 concurrency evidence exists in `tests/postgres/`** (`test_refund_threshold_concurrency`, `test_event_sequence_concurrency`, `test_operator_concurrency`, plus post-intent contention coverage). That evidence is pinned to PostgreSQL 16.4 via `tests/postgres/conftest.py::TESTED_POSTGRESQL_VERSION` and does **not** generalise to other PostgreSQL major versions, managed/cloud variants, or different lock/scheduling behaviour without re-running those proofs.

Event `seq` allocation uses the atomic `event_sequences` counter; the customer-row `FOR UPDATE` still serialises policy evaluation and history reads per customer on PostgreSQL. SQLite parses and ignores that lock.

The closed ordered policy list in one function is the right call while there is exactly one policy, and the wrong one the moment policies vary per tenant or arrive from configuration; at that point the question this design avoids — what to do when several rules fire on the same event — has to be answered properly.
