# SafeRefundAgent — Architecture Specification

This document is the normative description of the system as implemented. Where a design
choice looks arbitrary, §19 (*Design Decisions*) explains why it was made that way. Anything
genuinely uncovered by this document is recorded in `DEBT.md` rather than left implicit. §20
states what is deliberately out of scope.

**Claims registry.** Every normative claim in this document that has a runtime guard or a
documented convention-only boundary is indexed in [`docs/CLAIMS.md`](CLAIMS.md), one row
per claim, with the enforcing mechanism and guard test (or the `DEBT.md` bullet, for
convention-only claims) named explicitly. `tests/invariants/test_claims_registry_integrity.py`
checks that every row's pointer is live. If you add or change a load-bearing claim here, add
or update its row in `docs/CLAIMS.md` in the same change.

## 1. What this is

A support agent for an online shop that resolves refund requests arriving by email. All external systems are mocked. The language model is replaceable by a deterministic stub.

The subject of the design is not the agent. It is the enforcement boundary around it: an untrusted, potentially manipulated component proposes actions, and a deterministic gate decides whether each proposal reaches the side-effecting world, using the accumulated history of the case rather than the arguments of the current call.

Two properties must be visible in the code and demonstrable by tests:

1. **Structural elimination.** Whole classes of abuse are impossible because no argument exists that could express them — not because a check rejects them.
2. **Path dependence.** At least two rules depend on what happened earlier, not on the arguments of the proposed action.

## 2. Trust Model (normative)

### 2.1 Classification by provenance, not by type

**Untrusted — human-authored free text, wherever it comes from:**
email subject and body; `Order.item`; `Customer.name`; every free-text field of model output (`SendReply.subject`, `SendReply.body`, `Escalate.reason`, `Finish.summary`); the operator's `reason` on a rejection.

**Trusted — system-originated or system-computed:**
the sender identity taken from the transport envelope; identifiers assigned by `saferefund/ids.py`; enum values; amounts, totals and statuses loaded from seed rows; verification tokens generated by the gate; provider references returned by adapters; `actor` and `channel` assigned by trusted application code.

**Claims — untrusted until validated, canonical afterwards:**
`LinkOrder.order_id` and `ProposeRefund.amount` arrive as untrusted assertions from the model. `R_ORDER_OWNERSHIP` and `R_AMOUNT_SANE`/`R_REMAINDER` convert them into trusted facts. Only the validated form is ever written to an event and only the validated form is ever folded.

This is why the invariant below speaks of *validated canonical events*, not of string types. A `str` is not untrusted because it is a `str`; `provider_ref` and `order_id` are strings and are perfectly trustworthy.

### 2.2 The invariant

> **Authorisation decisions are computed only from seed rows and from canonical events emitted by trusted application code after validation.**
>
> No free-text payload field is ever read by a projection. An untrusted proposal may select among the transitions currently permitted to it, and its validated effects therefore become part of future control state — but it cannot bypass ownership, amount, verification, approval, or lifecycle rules, and it cannot introduce a fact the gate did not itself authorise.

Checkable by reading `saferefund/projections/`: those modules take seed rows and `Sequence[Event]` and nothing else, and no projection field reads `body`, `subject`, `reason`, `summary`, `item` or `name`.

### 2.3 What this does and does not buy

Prompt injection cannot escalate privilege. It **can** steer the agent among actions that are already permitted, and it can therefore consume the permitted budget — propose a legitimate refund for the wrong reason, send a reply with damaging content, burn the step allowance. The blast radius is exactly whatever the policy allows, which is the argument for keeping the allowed envelope narrow rather than for claiming injection is solved.

Case memory is rendered as bounded JSON with explicit `provenance` and `kind` fields. That framing helps the model distinguish historical data from gate outcomes, but it is **not** an enforcement control: provenance tags in the prompt cannot be trusted as security boundaries because untrusted text is neutralized and escaped rather than interpreted. The enforcement claim rests entirely on §2.2 — authorisation decisions are computed only from seed rows and canonical events after validation.

State this honestly in the README. Overclaiming here is the easiest way to lose credibility in the walkthrough.

### 3.2 Human-readable code is a normative deliverable

The implementation is reviewed in a short walkthrough. A reviewer must be able to understand the ordinary control flow from module structure, function boundaries, types and names **without depending on explanatory comments**. Readability is part of correctness for this artifact, not presentation polish performed after the behaviour works.

Apply these rules throughout Core and Stretch:

- **Use domain language in identifiers.** Prefer `pending_refund`, `customer_event_stream`, `refundable_remainder`, `append_refund_executed` and `resume_unblocked_cases` over generic names such as `data`, `item`, `result`, `process`, `handle` or `do_work`. Names must expose scope where confusion is possible: `case_events`, `customer_events`, `linked_order`, `operator_reason`.
- **Make units and representations visible.** A name should distinguish `approval_expires_at`, `approval_ttl_seconds`, `refund_amount`, raw model text and a parsed `Action`. Do not rely on a nearby comment to repair an ambiguous name.
- **Keep one level of abstraction per function.** Public gate operations and the agent loop should read top-to-bottom as domain orchestration. Move SQL details, payload construction and adapter-specific mechanics into narrowly named helpers. Do not mix a business decision, a query-building trick and response formatting in one block.
- **Prefer explicit domain types and exhaustive control flow.** Enums, frozen summaries, Pydantic action models, verdict dataclasses and `match` statements should carry meaning that would otherwise live in prose. Do not encode lifecycle state in loosely related booleans or magic strings.
- **Keep control flow linear.** Use early returns for guard conditions, shallow nesting, and named predicates for non-trivial conditions. Avoid clever comprehensions, nested ternaries, boolean puzzles, mutation hidden inside expressions, or metaprogramming that makes the execution path harder to follow.
- **Abstract only repeated concepts, not merely repeated syntax.** A small amount of explicit duplication is preferable to a generic helper whose parameters hide that two operations have different trust, transaction or event semantics. In particular, do not erase the asymmetry of `RequireApproval`, payment ordering, or actor/channel assignment behind a broad framework.
- **Comments explain why, never what.** Keep comments for policy precedence, concurrency guarantees, trust provenance, crash windows, or a deliberate divergence from the obvious implementation. Remove comments that translate the next line into English, narrate loops, or compensate for weak names and structure. A comment that can be replaced by a better identifier or helper boundary must be replaced.
- **Docstrings state contracts and properties.** Public boundary operations may have short docstrings describing preconditions, effects and failure semantics. Integration-test docstrings name the architectural property proved. Do not add file-wide or per-function narration solely to make Ruff happy.
- **Tests must read as scenarios.** Test names, fixture names and assertion helpers should expose setup, transition and expected outcome. Prefer `assert_case_event_types(...)` to repeated index arithmetic, provided the helper does not hide the complete sequence being asserted.

A practical review test: temporarily ignore the comments and read the changed module from top to bottom. If the main path, state transitions, ownership scope, or effect ordering is no longer obvious, the structure or identifiers must be improved before the step is complete.

## 4. Data Model

**Six tables.** Two hold immutable seed data (enforced by ORM listeners on `CustomerRow` and `OrderRow`, §4.7), one is the append-only log (same on `EventRow`), one is a materialised aggregate, one is a bare correlation row, and one — `event_sequences` (§14.3) — is a per-customer `next_seq` counter keyed by `customer_id` that allocates each event's `seq`.

### 4.1 `customers` — seed, immutable at runtime

Enforced in-process by `before_update` / `before_delete` listeners that raise `ImmutableRowError` (§4.7).

| Column | Type | Notes |
|---|---|---|
| `id` | `str` PK | e.g. `cust_sophie` |
| `email` | `str`, UNIQUE, NOT NULL | lowercased on write and on every lookup |
| `name` | `str` | untrusted free text |

There is **no `verified` column.** Verification is folded from events (§7.1).

### 4.2 `orders` — seed, immutable at runtime

Enforced in-process by the same ORM listeners as `customers` (§4.7).

| Column | Type | Notes |
|---|---|---|
| `id` | `str` PK | e.g. `ORD-1001` |
| `customer_id` | `str` FK → `customers.id`, NOT NULL | |
| `item` | `str` | untrusted free text |
| `total` | `Numeric(12,2)`, NOT NULL | named `total` everywhere, never `amount` |
| `status` | `str` | `delivered`, `delivered_damaged`, `shipped` |

Refund history is not a column here; it is folded from events (§7.2).

> `Order.status` is **advisory input to the model only.** The policy deliberately does not gate refund eligibility on it. Do not add a status-based rule.

### 4.3 `events` — append-only, source of truth

Enforced in-process by the same ORM listeners (§4.7).

| Column | Type | Notes |
|---|---|---|
| `id` | `str` PK | |
| `customer_id` | `str` FK, NOT NULL | every event is customer-scoped at minimum |
| `case_id` | `str` FK, NULL | |
| `order_id` | `str` FK, NULL | |
| `seq` | `int`, NOT NULL | monotonic per customer, assigned per §14.3 |
| `type` | `str`, NOT NULL | from the §6 catalogue; no other value is legal |
| `actor` | enum `customer` \| `agent` \| `operator` \| `system`, NOT NULL | |
| `channel` | enum `email` \| `operator_api` \| `verification_api` \| `internal`, NOT NULL | |
| `payload` | JSON, NOT NULL | Pydantic-validated per type on write |
| `created_at` | `datetime` UTC, NOT NULL | from `clock.now()` |

Constraint: `UNIQUE(customer_id, seq)`. Application code does not issue `UPDATE` or `DELETE` against this table; in-process ORM sessions are additionally blocked by `ImmutableRowError` (§4.7).

> **Provenance of `actor` and `channel` (normative).** Both are assigned by trusted application code according to the entry point and operation being performed — the route for inbound requests, the gate for agent and system events, the seeder for seed events. **Neither is ever accepted as a request field or read from model output.** Authentication of the claimed operator identity is out of scope (§13.5); the integrity guarantee here is that the *category* of actor is determined by which code path ran, not by anything the caller or the model said.

### 4.4 `refunds` — materialised aggregate

| Column | Type | Notes |
|---|---|---|
| `id` | `str` PK | `rfnd_…`; doubles as the payment idempotency key |
| `order_id` | `str` FK, NOT NULL | |
| `case_id` | `str` FK, NOT NULL | |
| `amount` | `Numeric(12,2)`, NOT NULL | |
| `status` | enum `pending_approval` \| `approved` \| `executed` \| `rejected` \| `expired`, NOT NULL | |
| `approval_expires_at` | `datetime`, NULL | set only while `pending_approval` |
| `created_at` | `datetime`, NOT NULL | |

**Partial unique index:**

```sql
CREATE UNIQUE INDEX uq_open_refund_per_order
  ON refunds (order_id)
  WHERE status IN ('pending_approval', 'approved');
```

> **Documented exception to §2.2.** Every other piece of control state is folded from `events`. `refunds` is a real row with a mutable status because a database constraint is the only mechanism that holds an invariant against code that has not been written yet, including code added later by someone who has not read this document. An append-only log cannot express *at most one open refund per order*. Every lifecycle transition of a refund row is also written as an event (§6, §11); the row is the enforcement surface, the events are the evidence. If they ever disagree, the events are right and the row is a bug.

### 4.5 `cases`

| Column | Type | Notes |
|---|---|---|
| `id` | `str` PK | |
| `customer_id` | `str` FK, NOT NULL | |
| `opening_message_id` | `str`, NOT NULL | sender-controlled identifier; unique per customer with `customer_id` |
| `created_at` | `datetime`, NOT NULL | |

No status, no counters, no linked order — all folded (§7.3). `CaseRow` is **not** guarded by the immutability listeners: the documents call only seeds and the event log immutable, and no code updates `cases` today.

### 4.6 What is deliberately not a table

There is no `PersonalAgent` entity. Conversational memory is rendered from the customer's event stream (§12.4). A second store of "memory" beside the event log means two sources of truth, and the second one is the one fed by untrusted text.

### 4.7 Immutability enforcement (ORM boundary)

`CustomerRow`, `OrderRow`, and `EventRow` register SQLAlchemy `before_update` and `before_delete` mapper listeners that raise `ImmutableRowError`. `before_update` fires only when a net change is detected, so reads and no-op flushes are unaffected. `RefundRow` stays mutable — it is the enforcement surface (§4.4).

This binds writes that go through a SQLAlchemy session **in this process**. It does not bind raw SQL, another process, a DBA, or a migration. The production form is `REVOKE UPDATE, DELETE` plus append-only triggers or a WORM store; see `DEBT.md`.

## 5. Case Model and Inbound Routing (normative)

**One inbound email opens exactly one case per customer.** The dedupe key is the pair `(customer_id, opening_message_id)`. A `message_id` reused by a different sender is not a collision — it opens that sender's own case.

- Unknown `(customer_id, message_id)` → create a case, append `case_opened` and `email_received`, run the loop.
- Known `(customer_id, message_id)` → append no event. If the existing case is still `open`, run the loop again, which makes delivery retries safe after a crash mid-run. If it is not `open`, return its current state unchanged.

**Email threading into an existing case is out of scope.** A follow-up email opens a new case; refund history lives on the order and therefore survives case boundaries, so the cumulative threshold cannot be defeated by opening a fresh case. Record the omission in `DEBT.md`.

A customer may have several cases open at once. Everything case-scoped is folded strictly per case (§7.4).

## 6. Event Catalogue

Exhaustive and normative, including actor and channel. A `type` outside this table is a bug; an actor/channel pair outside this table is a bug. Payload schemas live in `saferefund/domain/payloads.py`.

| `type` | Scope | Actor | Channel | Payload |
|---|---|---|---|---|
| `case_opened` | case | system | internal | `{opening_message_id}` |
| `email_received` | case | customer | email | `{message_id, subject, body}` |
| `orders_listed` | case | agent | internal | `{order_ids: [str]}` |
| `order_linked` | case + order | agent | internal | `{order_id}` |
| `verification_requested` | case | agent | internal | `{token, expires_at}` |
| `customer_verified` | customer | system | `internal` if `method=seed`, `verification_api` if `method=token` | `{method}` |
| `refund_proposed` | case + order | agent | internal | `{refund_id, amount}` |
| `refund_auto_approved` | case + order | system | internal | `{refund_id}` |
| `refund_approval_required` | case + order | system | internal | `{refund_id, amount, rule}` |
| `refund_approved` | case + order | operator | operator_api | `{refund_id, operator_id}` |
| `refund_rejected` | case + order | operator | operator_api | `{refund_id, operator_id, reason}` |
| `refund_expired` | case + order | system | internal | `{refund_id}` |
| `refund_executed` | case + order | system | internal | `{refund_id, amount, provider_ref}` |
| `reply_sent` | case | agent | internal | `{subject, body}` |
| `escalated` | case | `agent` if `origin=agent`, else `system` | internal | `{reason, origin, ticket_id}` |
| `action_denied` | case | system | internal | `{action, rule, agent_reason, customer_reason}` |
| `invalid_output` | case | system | internal | `{preview, byte_count, sha256, error}` |
| `case_closed` | case | system | internal | `{outcome, summary}` |

`escalated.origin` ∈ `agent` \| `policy` \| `step_limit` \| `parse_limit` \| `model_failure`.
`case_closed.outcome` ∈ `finished` \| `escalated` \| `step_limit` \| `parse_limit` \| `model_failure`.
`case_closed.summary` is `str | None`; it carries `Finish.summary`, otherwise `None`.

> **`escalated` is always immediately followed by `case_closed` in the same gate operation.** There is no state in which a case has been escalated and remains open. See §9.2.

`action_denied`, `invalid_output`, `refund_auto_approved`, `refund_approval_required` and `case_closed` carry `actor=system` although the agent triggered them. The actor field answers *who is accountable for this state change*, not *what caused it*.

`customer_verified` is customer-scoped (`case_id` NULL) because verification is a property of the customer. The case that issued the token is found from the `verification_requested` event carrying it (§13.4).

## 7. Projections

Pure functions in `saferefund/projections/`. Shape: `(seed_rows, Sequence[Event], now) -> Frozen…Summary`. No I/O, no clock access other than the passed-in `now`. Recomputed on every load; no cache. Events are folded in ascending `seq`.

### 7.1 `CustomerSummary`

```python
@dataclass(frozen=True, slots=True)
class CustomerSummary:
    customer_id: str
    email: str
    verified: bool
```

Fold: `customer_verified` → `verified = True`. Nothing else.

### 7.2 `OrderSummary`

```python
@dataclass(frozen=True, slots=True)
class OrderSummary:
    order_id: str
    customer_id: str
    total: Decimal
    refunded_total: Decimal
    has_open_refund: bool

    @property
    def refundable_remainder(self) -> Decimal:
        return self.total - self.refunded_total
```

Fold: `refund_executed` → `refunded_total += amount` **and** `has_open_refund = False`. `refund_proposed` → `has_open_refund = True`. `refund_rejected`, `refund_expired` → `has_open_refund = False`.

Folds all events for the order **across every case**. Refund history outlives the case that produced it, which is what makes the cumulative threshold resistant to opening a new case.

### 7.3 `CaseSummary`

```python
@dataclass(frozen=True, slots=True)
class CaseSummary:
    case_id: str
    customer_id: str
    status: CaseStatus          # open | awaiting_approval | awaiting_verification | closed
    linked_order_id: str | None
    orders_listed: bool
    step_count: int
    consecutive_denials: int
    consecutive_invalid_outputs: int
    last_refund_status: RefundStatus | None
    reply_sent_after_last_refund: bool
```

Private fold state (`_CaseFoldState`) retains `pending_refund_id`, `verification_token`, and `verification_expires_at` for status precedence only. They are **not** exposed on the public summary handed to prompt assembly, so a live verification token cannot leak through `repr()` or structured state.

Fold rules:

- `step_count` — `+1` per agent model attempt that reaches an outcome: successful action events (`orders_listed`, `order_linked`, `verification_requested`, `reply_sent`, `refund_proposed`, `case_closed{finished}`), `action_denied`, `invalid_output`, and `escalated` when `origin ∈ {agent, policy}`. Companion lifecycle events such as `refund_approval_required`, and `case_closed` after an escalation, do not add a second step. `actor` records accountability, not causation.
- `consecutive_denials` — `+1` on `action_denied`; reset to `0` on an allowed agent outcome. A policy denial-loop escalation closes the case but preserves the three-denial streak as evidence.
- `consecutive_invalid_outputs` — `+1` on `invalid_output`; **reset to `0` on any successful parse outcome and also on `action_denied`.** A denied action was parsed successfully; it is a parser success and a policy failure, and only the parser counter cares. Without the second reset condition an alternating sequence of malformed output and denied actions reaches the parse limit while the parser is in fact working.
- `linked_order_id` — the `order_id` of the most recent `order_linked`. Re-linking is permitted and is itself an event.
- Private fold state tracks `pending_refund_id` from `refund_approval_required` until resolution, and `verification_token` / `verification_expires_at` from the most recent `verification_requested`, solely to evaluate status precedence below.
- `last_refund_status` — status of the most recently proposed refund of this case, derived from its events: `refund_proposed` → `pending_approval`; `refund_auto_approved` / `refund_approved` → `approved`; `refund_executed` → `executed`; `refund_rejected` → `rejected`; `refund_expired` → `expired`.
- `reply_sent_after_last_refund` — `True` if a `reply_sent` occurred after the most recent refund-lifecycle event of this case.
- `status`, evaluated in this precedence order:
  1. `closed` — a `case_closed` exists.
  2. `awaiting_approval` — private fold `pending_refund_id is not None`.
  3. `awaiting_verification` — a `verification_requested` exists, the customer is not verified, **and** private fold `now < verification_expires_at`.
  4. `open` — otherwise.

Consequence of 3: an expired verification request stops making the case wait; the case returns to `open` by itself. That is what prevents a permanently suspended case.

`last_refund_status` and `reply_sent_after_last_refund` exist for one reason: to make the deterministic stub model a total function of state (§12.6). They are not read by any rule.

### 7.4 Scoping contract (normative)

> `CustomerSummary` folds events where `event.customer_id == customer_id` **and** the type is customer-scoped per §6.
> `CaseSummary` folds events where `event.case_id == case_id`, plus exactly one customer-scoped fact: `customer_verified`, used only to evaluate status precedence 3.
> `OrderSummary` folds events where `event.order_id == order_id`.
> **Events belonging to another case must never influence a `CaseSummary`.** A unit test asserts this with two concurrent cases for one customer.

## 8. Action Model

Actions are values, not calls. The model never invokes anything; it emits JSON parsed into one of these. Pydantic v2 discriminated union on `action`, `extra="forbid"`.

```python
class GetOrders(BaseModel):
    action: Literal["get_orders"]

class LinkOrder(BaseModel):
    action: Literal["link_order"]
    order_id: str

class ProposeRefund(BaseModel):
    action: Literal["propose_refund"]
    amount: Decimal

class SendReply(BaseModel):
    action: Literal["send_reply"]
    subject: str
    body: str

class RequestVerification(BaseModel):
    action: Literal["request_verification"]

class Escalate(BaseModel):
    action: Literal["escalate"]
    reason: str

class Finish(BaseModel):
    action: Literal["finish"]
    summary: str

type Action = (
    GetOrders | LinkOrder | ProposeRefund | SendReply
    | RequestVerification | Escalate | Finish
)
```

`ProposeRefund.amount` is parsed as `Decimal` **without quantisation**, so `R_AMOUNT_SANE` can still observe an illegal scale or a non-finite value. Quantisation to two places happens once, immediately before persistence.

### 8.1 What is absent, and why

| Absent parameter | Consequence |
|---|---|
| any customer identity or email address | Cross-customer access is not expressible. |
| recipient on `send_reply` | Exfiltration to an arbitrary address is not expressible; the recipient is resolved from the case. |
| `order_id` on `propose_refund` | The refund targets `case.linked_order_id`. Refunding an order the case never established is not expressible. |

`order_id` survives on `link_order` alone, where `R_ORDER_OWNERSHIP` validates it against the customer's own orders. **This is the only place in the system where model output names a domain object**, and therefore the only place an ownership check is required.

### 8.2 Labels

Static properties of the action *type*, maintained in `tests/unit/labels_helpers.py` as a mapping from class to `frozenset[Label]`. Never arguments, never model-supplied. This mapping is a **test and documentation invariant** — no production code reads it; policy obligations in §10 are table-driven.

| Action | Labels |
|---|---|
| `get_orders` | `READS_PII` |
| `link_order` | `READS_PII` |
| `propose_refund` | `MOVES_MONEY` |
| `send_reply` | `EXTERNAL_COMM` |
| `request_verification` | `EXTERNAL_COMM` |
| `escalate` | `INTERNAL_SIDE_EFFECT` |
| `finish` | `TERMINAL` |

`request_verification` carries `EXTERNAL_COMM` but not `READS_PII`, which is precisely what leaves it available to an unverified customer under `R_VERIFIED`.

`escalate` carries `INTERNAL_SIDE_EFFECT` because it calls the ticketing adapter. `EXTERNAL_COMM` in this vocabulary means *a message crosses the boundary to the customer*; ticketing is an internal system and therefore belongs to a different effect class. The label is a documentation/test invariant only — policy obligations are table-driven and labels do not route rules. The effect is still mediated by the gate, but there is no policy obligation that expresses or limits escalation across cases, customers or time windows. `MAX_AGENT_STEPS` is only a local per-case cap and must not be presented as a system-wide anti-spam guarantee.

> **Trust note for the writeup.** Labels are the trusted classification boundary. Here they are static per action type and therefore trivially correct. In a real system they depend on runtime payload properties, and whoever assigns them becomes the highest-value target in the architecture.

### 8.3 Action → events produced (normative)

Applies when the action parsed successfully **and** the gate accepted it. Denials and forced escalations are covered by §9.2.

| Action | Events, in order | Actor(s) |
|---|---|---|
| `get_orders` | `orders_listed` | agent |
| `link_order` | `order_linked` | agent |
| `propose_refund` | `refund_proposed`, then `refund_auto_approved` + `refund_executed` (verdict `Allow`) **or** `refund_approval_required` (verdict `RequireApproval`) | agent, then system |
| `send_reply` | `reply_sent` | agent |
| `request_verification` | `verification_requested` | agent |
| `escalate` | `escalated{origin=agent, ticket_id}`, then `case_closed{outcome=escalated}` | agent, then system |
| `finish` | `case_closed{outcome=finished, summary}` | system |

Note that `propose_refund` is the only action for which `RequireApproval` is an *accepting* verdict: the proposal is persisted and the money is withheld. Every other action treats a non-`Allow` verdict as a refusal.

## 9. Gate — the application boundary

`saferefund/gate/` is the only module permitted to **invoke** `saferefund/adapters/` effect entry points (`send`, `refund`, `escalate`). It exports **seven** mediated operations through its façade; untrusted layers (`api`, `agent`) reach only those entry points, not the gate's internal effect helpers or verdict dispatch modules. Import-linter contracts (§16) are **layering hygiene** — they catch accidental imports at review time but do not stop a determined in-process bypass; the integration suite's call-origin fixture exercises the mediation claim across scenarios. **Rung 5** (§16): private effect helpers require a spent `Authorisation` minted only by `policy.authorise` after a full `Allow`; `RequireApproval` and `ForceEscalate` dispatch on their verdict objects without fabricating capabilities. Trusted system escalations (step/parse/model-failure limits) use `escalate_case` without a model `Action`. That stops accidents and makes deliberate bypass review-visible but is not a process boundary. `demo.py` imports `mailer.snapshot_outbox()` read-only as a documented exception. Database event appends are **not** mediated — the API and the agent loop append `invalid_output` and other housekeeping events directly via `repositories`.

```python
async def execute_agent_action(
    session: AsyncSession,
    case_id: str,
    action: Action,
    *,
    session_factory: async_sessionmaker[AsyncSession] | None = None,
) -> Verdict
async def escalate_case(
    session: AsyncSession,
    case_id: str,
    *,
    origin: EscalationOrigin,
    reason: str | None = None,
    authorisation: Authorisation | None = None,
    force_escalate: ForceEscalate | None = None,
) -> None
async def expire_due_refunds_for_customer(session: AsyncSession, *, customer_id: str) -> tuple[str, ...]
async def approve_refund(
    session: AsyncSession,
    refund_id: str,
    operator_id: str,
    *,
    session_factory: async_sessionmaker[AsyncSession] | None = None,
) -> OperatorOutcome
async def reject_refund(session: AsyncSession, refund_id: str, operator_id: str, reason: str) -> OperatorOutcome
async def confirm_verification(session: AsyncSession, token: str) -> VerificationOutcome
async def send_unknown_sender_reply(email: str) -> None
```

`escalate_case` exists because the agent loop must be able to escalate on a hard limit, and doing so requires a ticket id from the ticketing adapter, which the loop may not import. It derives the event actor from `origin`: `agent` for `origin=agent`, `system` otherwise. It always appends `escalated` **and** `case_closed` together. `origin=agent` requires an unspent `Authorisation` whose bound action is the exact `Escalate` proposal; the ticket/event reason is taken from that action. `origin=policy` requires a `ForceEscalate` verdict object; the ticket/event reason is taken from that verdict. Trusted system origins (`step_limit`, `parse_limit`, `model_failure`) take an explicit `reason` and accept no capability evidence.

`execute_agent_action` takes **no `actor` argument**: an agent action is always `Actor.AGENT`, and accepting the actor from the caller would create a substitution point for the one field the whole trust model rests on.

`execute_agent_action` has a precondition checked *inside* the gate, not assumed of the caller: the case must be `open`. It is enforced by `R_CASE_NOT_ACTIONABLE` rather than an assertion, so a caller mistake produces an ordinary, logged denial.

### 9.1 `execute_agent_action` algorithm

1. Load seed rows and the customer's event stream.
2. Build `CustomerSummary`, `CaseSummary`, and the linked `OrderSummary` if any.
3. `authorise(ctx, action)` (§10): on `Allow`, mint a single-use `Authorisation` — the **only** normal production mint site; return `Deny`, `RequireApproval`, and `ForceEscalate` unchanged.
4. Dispatch on `(verdict_or_authorisation, action)` per §9.2. `Allow`-backed paths return `Allow` as an audit **report** after spending the minted `Authorisation` (or after locked re-evaluation for refunds). Non-`Allow` verdicts dispatch on their own evidence.

Lazy approval expiry runs at loop entry and on inbound traffic (§11.2) before this function is reached on resume paths.

### 9.2 Verdict dispatch (normative)

| Verdict | Action | Effect |
|---|---|---|
| `Deny` | any | append `action_denied{action, rule, agent_reason, customer_reason}`; nothing else happens |
| `ForceEscalate` | any | `escalate_case(origin=policy, force_escalate=verdict)` → `escalated` + `case_closed{escalated}` |
| `RequireApproval` | `propose_refund` | run the refund transaction of §14.1 with the pending branch under customer lock via `authorise` (locked result is authoritative) |
| `RequireApproval` | anything else | unreachable — only `MOVES_MONEY` actions can produce it. `assert_never`-equivalent guard. |
| `Allow` | `propose_refund` | run the refund transaction of §14.1; locked `authorise` under customer lock spends a fresh `Authorisation` before auto-approval/payment |
| `Allow` | `escalate` | `escalate_case(origin=agent, authorisation=…)` |
| `Allow` | `finish` | append `case_closed{outcome=finished, summary=action.summary}` |
| `Allow` | anything else | invoke the private adapter, append the single success event from §8.3 |

### 9.3 Verdicts

```python
class Continue(Enum):
    TOKEN = auto()

CONTINUE: Final = Continue.TOKEN

@dataclass(frozen=True, slots=True)
class Allow: ...

@dataclass(frozen=True, slots=True)
class Deny:
    rule: str
    agent_reason: str
    customer_reason: str

@dataclass(frozen=True, slots=True)
class RequireApproval:
    rule: str
    reason: str

@dataclass(frozen=True, slots=True)
class ForceEscalate:
    rule: str
    reason: str

type Verdict = Allow | Deny | RequireApproval | ForceEscalate
type CheckResult = Continue | Deny | RequireApproval | ForceEscalate
```

Checks return only refusals or suspension signals. Only ``evaluate`` may produce ``Allow`` after every applicable obligation passes.

Dispatch uses `match` with `assert_never` in the default arm. `isinstance` is not used for verdict dispatch anywhere.

`Deny` carries two texts deliberately. `agent_reason` enters the model's memory so it can adapt; `customer_reason` is what may reach the customer. They are allowed to differ, because a denial reason is a policy-disclosure channel and the model's context is steered by attacker-controlled text.

### 9.4 Ordering of non-payment side effects

Payment follows a record-before-effect protocol (§14.1) because moving money without a durable intent record is unacceptable. The mocked mailer and ticketing adapters deliberately use the simpler **effect-first, event-second** order:

1. call `mailer.send(...)` or `ticketing.escalate(...)`;
2. if the adapter succeeds, append the corresponding event or events.

This order keeps the toy implementation small and makes each success event mean that the mocked adapter returned successfully. It also creates a known crash window: a reply or verification message may be delivered without `reply_sent` or `verification_requested`; a ticket may be created without `escalated`; a retry may therefore duplicate a message, issue a replacement verification token, or create an orphan ticket. No transactional outbox or adapter reconciliation is implemented. The limitation is stated explicitly in `DEBT.md`; do not silently reverse the order in implementation, because that would change the specified failure semantics.

## 10. Policy

The entire policy is one generator in `saferefund/policy/policy.py`. Reading it top to bottom *is* reading the policy, including precedence.

### 10.1 Rule context

```python
@dataclass(frozen=True, slots=True)
class RuleContext:
    now: datetime
    customer: CustomerSummary
    case: CaseSummary
    linked_order: OrderSummary | None
    customer_order_ids: frozenset[str]
    refund_approval_threshold: Decimal
    denial_loop_threshold: int
```

Configuration enters through the context, never by importing `config` inside a check. Checks are pure functions of their arguments.

### 10.2 Ordering contract (normative)

> Every check that can return `Deny` or `ForceEscalate` must appear above every check that can return `RequireApproval`.
>
> Rationale: `RequireApproval` short-circuits the run. A prohibition placed below it never executes, and the action is routed to a human in a situation where the system was required to refuse by itself. This is not a false *allow*, but it silently converts a policy decision into an operator decision — and the operator sees a request the system has implicitly endorsed.

The normative evaluation order is `CANONICAL_ORDER` in `saferefund/policy/checks.py`, declared exactly once. The driver walks that tuple for every action type; per-type tables select which obligations apply, they do not reorder them.

Guarded by a test (§17.3), not only by the comment.

Policy is a **conjunction of obligations**: permission means every applicable obligation returned `CONTINUE`. Check polarity is deny-first by construction (`deny_if_*` returns `Deny` on violation). The fail-closed guarantee lives at the **coverage** layer: an action type with no signed `ACTION_OBLIGATIONS` entry is denied `R_EXHAUSTED`; an entry with an empty `required` set is an explicit decision that only universal obligations apply.

### 10.3 The policy

```python
UNIVERSAL_OBLIGATIONS = (ObligationId.CASE_ACTIONABLE, ObligationId.DENIAL_LOOP)

ACTION_OBLIGATIONS: dict[type[_ActionBase], Obligations] = {
    GetOrders: Obligations(frozenset({ObligationId.VERIFIED}), "..."),
    LinkOrder: Obligations(frozenset({VERIFIED, ORDER_OWNED}), "..."),
    ProposeRefund: Obligations(
        frozenset({VERIFIED, LINKED_ORDER, AMOUNT_SANE, NO_OPEN_REFUND,
                   WITHIN_REMAINDER, THRESHOLD}),
        "...",
    ),
    RequestVerification: Obligations(frozenset({NOT_ALREADY_VERIFIED}), "..."),
    SendReply: Obligations(frozenset(), "..."),
    Escalate: Obligations(frozenset(), "..."),
    Finish: Obligations(frozenset(), "..."),
}

CHECKS: dict[ObligationId, Check]  # uniform (RuleContext, Action) -> CheckResult
```

Applicability is entirely in `ACTION_OBLIGATIONS` plus `UNIVERSAL_OBLIGATIONS`. Action labels (§8.2) are not consulted at runtime.

### 10.4 Driver — fail-closed

```python
def evaluate(ctx: RuleContext, action: Action) -> Verdict:
    obligations = ACTION_OBLIGATIONS.get(type(action))
    if obligations is None:
        return Deny(rule="R_EXHAUSTED", ...)   # uncovered action type

    applicable = frozenset(UNIVERSAL_OBLIGATIONS) | obligations.required
    for obligation_id in CANONICAL_ORDER:
        if obligation_id in applicable:
            result = CHECKS[obligation_id](ctx, action)
            if result is not CONTINUE:
                return result
    return Allow()                            # the only Allow in the system
```

`CheckResult` excludes `Allow`; only `evaluate` may authorise. An action type absent from `ACTION_OBLIGATIONS` — including one whose author forgot to record a coverage decision — is denied `R_EXHAUSTED`. An entry with `required=frozenset()` is truthy and means "no type-specific obligations beyond the universal pair"; it is not the same as a missing key. There is no fall-through allow.

### 10.5 Checks

Pure functions `(...) -> CheckResult` in `saferefund/policy/checks.py`, unit-tested in isolation. Rule IDs are stable strings appearing verbatim in `action_denied.rule`.

| ID | Condition | Verdict |
|---|---|---|
| `R_CASE_NOT_ACTIONABLE` | `case.status is not CaseStatus.OPEN` | `Deny` |
| `R_DENIAL_LOOP` | `case.consecutive_denials >= ctx.denial_loop_threshold` | `ForceEscalate` |
| `R_VERIFIED` | action has `MOVES_MONEY` or `READS_PII` and `not customer.verified` | `Deny`; `agent_reason` states that `request_verification` is the only action that unlocks order data and refunds, and that replying, escalating and finishing remain available |
| `R_ALREADY_VERIFIED` | action is `request_verification` and `customer.verified` | `Deny` |
| `R_ORDER_OWNERSHIP` | `action.order_id not in ctx.customer_order_ids` | `Deny` |
| `R_NO_LINKED_ORDER` | `case.linked_order_id is None` | `Deny` |
| `R_AMOUNT_SANE` | `not amount.is_finite()` (rejects `NaN`, `Infinity`, `-Infinity`) **or** `amount <= 0` **or** `amount.as_tuple().exponent < -2` | `Deny` |
| `R_OPEN_REFUND` | `order.has_open_refund` | `Deny` |
| `R_REMAINDER` | `amount > order.refundable_remainder` | `Deny` |
| `R_THRESHOLD` | `order.refunded_total + amount > ctx.refund_approval_threshold` | `RequireApproval` |

`R_AMOUNT_SANE` must test finiteness **first**; comparison operators on `NaN` are silently false and would let it through.

`R_OPEN_REFUND` deliberately duplicates the partial unique index of §4.4. The rule produces a comprehensible message; the index produces the guarantee.

`R_THRESHOLD` is the rule the architecture exists for: it reads `refunded_total`, not `action.amount`. Splitting 800 into 300 + 300 + 200 does not evade it. The threshold arrives through `RuleContext`; the literal `500` appears only in `config.py`.

## 11. Refund Lifecycle and Verification Delivery

### 11.1 Refund states

```
propose_refund accepted
    └─ INSERT refunds(status=pending_approval)
       append refund_proposed
       ├─ verdict Allow            → status=approved,        append refund_auto_approved
       └─ verdict RequireApproval  → stays pending_approval, append refund_approval_required
                                        ├─ operator approves → status=approved,  append refund_approved
                                        ├─ operator rejects  → status=rejected,  append refund_rejected
                                        └─ TTL elapses       → status=expired,   append refund_expired

status == approved → payment call → status=executed, append refund_executed
```

- The row is created inside the same transaction that evaluated the policy (§14.1).
- `approval_expires_at = now + APPROVAL_TTL_SECONDS` while `pending_approval`; `NULL` in every other state.
- Approval is **one-shot and scoped to one `refund_id`**. It authorises exactly the amount on that row. It does not persist on the case, does not survive the refund, and does not apply to any later proposal. One-shot holds because the decisive status is read under the customer row lock (§14.3) after lazy expiry, and the `pending_approval` → `approved`/`rejected` transition is a guarded `UPDATE … WHERE status = 'pending_approval'`; `rowcount = 0` yields `409` even when `FOR UPDATE` is a no-op (SQLite).
- Payment never fails: the mock always succeeds. Provider failure handling is out of scope; do not add retries or a failure status.

### 11.2 Expiry — one entry point, four call sites

```python
async def expire_due_refunds_for_customer(
    session: AsyncSession, *, customer_id: str
) -> tuple[str, ...]
```

The approval window is the half-open interval `[created_at, approval_expires_at)`; `approval_expires_at` is the **first instant at which approval is refused**. The boundary is defined once in `repositories/refunds.py` as `approval_window_is_open` and its complementary SQL clause builders `active_pending_refund_clause` and `due_for_expiry_clause` (exact complements within `pending_approval`: `approval_expires_at > now` versus `approval_expires_at <= now`). Neither call site writes its own comparison operator.

Under the customer row lock, transitions every `pending_approval` refund for that customer whose window has closed (`due_for_expiry_clause(clock.now())`) to `expired`, appends `refund_expired` on each owning case, and returns the ids of cases that project to `open` after the sweep, in ascending `case_id` order (deduplicated when multiple due rows share a case). It is called from exactly four places and nowhere else:

1. `run_agent_loop` in `agent/loop.py` — at the top of each iteration, before loading loop context, so an `awaiting_approval` case can re-project to `open` and continue in the same call; non-current ids returned by the sweep are accumulated and handed back to the caller when the loop ends, never resumed while this case lock is held;
2. `post_inbound_email` in `api/routes.py` — after `find_customer_by_email` succeeds, inside the inbound transaction; routes then drain every returned open case through `_drain_agent_loop_queue` in ascending `case_id` order (committing and releasing each case lock before dequeuing peers), then the inbound case when it is still open and was not already queued;
3. `approve_refund` in `gate/operator.py` — after the customer row lock and before the status check that produces `409`;
4. `reject_refund` in `gate/operator.py` — after the customer row lock and before the status check that produces `409`.

Expiry therefore runs before the operator status check that yields `409`, and before the loop's status early-return on resume. Setup reads and the customer row lock may precede it in the operator paths.

`GET /operator/pending` **does not** call it and **does not** mutate anything; it filters closed-window rows out of its query with `active_pending_refund_clause(now())`. A read endpoint that silently changes state and then leaves a case un-resumed is the failure mode this avoids.

> Ordinary traffic from a customer — inbound mail, agent-loop resume, or operator approve/reject — reaps that customer's stale approvals. A customer who never writes again and has no operator still holds a stale approval indefinitely; there is no periodic sweeper (see `DEBT.md`). Production would add a cron job or outbox worker calling `expire_due_refunds_for_customer` for each customer with pending rows.

### 11.3 Verification delivery (normative)

`request_verification` is not merely a state change; it has an external effect, and without one the out-of-band claim is empty.

On `Allow`, the gate:

1. generates `token = ids.verification_token()` and `expires_at = now + VERIFICATION_TTL_SECONDS`;
2. calls `mailer.send(to=<case customer email>, subject=VERIFICATION_SUBJECT, body=VERIFICATION_BODY.format(token=token))` — a fixed template constant, not model-authored text;
3. after the mailer returns successfully, appends `verification_requested{token, expires_at}`.

The effect-first ordering is deliberate and follows §9.4. A process failure after step 2 and before step 3 leaves the customer with an unusable token and no audit event; a retry can send a replacement token. This is accepted for the mocked artifact and recorded in `DEBT.md`, not hidden behind a claim of atomic delivery.

The token reaches the customer through the mailer outbox, which is what tests read. `make demo` prints the outbox alongside the event log so the token is visible without inspecting the database. `POST /verification/confirm` is the mock stand-in for the customer clicking the link.

## 12. Agent Loop

`saferefund/agent/loop.py`. Two phases per iteration: the model proposes a value, the gate decides.

### 12.0 Model gateway (trusted boundary)

Production model execution runs behind `ModelGateway`, owned by the trusted application boundary. `create_app` and `run_agent_loop` accept only `ModelGateway`; they do not accept arbitrary objects that merely expose `propose()`.

The default transport launches an isolated worker subprocess with a length-prefixed prompt-bytes/response-bytes protocol. The worker strips application source trees from `sys.path`, receives no database or adapter credentials, and applies configured wall-clock, CPU, memory, and response-size limits before returning bytes.

Deterministic tests use trusted gateway transports (`ScriptedModelGatewayTransport`, `HeuristicModelGatewayTransport`, and related fixtures) that return serialized responses without injecting executable model objects into production entry points. Import lint and call-origin fixtures remain defense-in-depth, not the primary isolation mechanism.

Trusted: gateway construction, transport selection, prompt serialization, and all gate handling after `ModelGateway.propose()` returns UTF-8 text. Untrusted: the worker/provider response bytes until the gateway boundary validates and hands text to the parser.

### 12.1 Hard limits

Properties of the loop, not policy. Not expressible as rules, not waivable, not routed through `evaluate`.

| Constant | Value | On breach |
|---|---|---|
| `MAX_AGENT_STEPS` | 12 | `gate.escalate_case(origin=step_limit, …)` → `escalated` + `case_closed{step_limit}`, exit |
| `MAX_INVALID_OUTPUTS` | 3 | `gate.escalate_case(origin=parse_limit, …)` → `escalated` + `case_closed{parse_limit}`, exit |
| `MODEL_CALL_TIMEOUT_SECONDS` | 30.0 | `gate.escalate_case(origin=model_failure, …)` → `escalated` + `case_closed{model_failure}`, exit |

Both counters come from `CaseSummary`, so both survive suspension and resumption: a case suspended at step 9 resumes at step 9.

Termination is via projected `CaseStatus` (`closed`, `awaiting_approval`, `awaiting_verification`), hard limits, model-boundary failure (`escalate_case` with `origin=model_failure`, including a wall-clock timeout on `model.propose`), or suspension. Every terminating path writes `case_closed`. Failures of the model call itself are caught at the boundary and close the case; database errors, adapter failures, and other infrastructure exceptions raised by `execute_agent_action` are not caught there — they propagate out of the loop and leave the case resumable so the evidence that something is wrong is preserved.

### 12.2 Loop body

```
while True:
    summary = load_case_summary()
    if summary.status is CLOSED: return
    if summary.status in (AWAITING_APPROVAL, AWAITING_VERIFICATION): return   # suspended
    if summary.step_count >= MAX_AGENT_STEPS:
        await gate.escalate_case(session, case_id, origin=STEP_LIMIT, reason=...); return
    if summary.consecutive_invalid_outputs >= MAX_INVALID_OUTPUTS:
        await gate.escalate_case(session, case_id, origin=PARSE_LIMIT, reason=...); return

    prompt = build_prompt(summary, disclosed_order_rows, seed_rows)
    boundary = await invoke_model_boundary(session, case_id=case_id,
                                           model_gateway=model_gateway, prompt=prompt)
    if boundary is None:
        return   # model_failure escalation already closed the case
    match boundary.outcome:
        case ParseFailure(err):
            append invalid_output with bounded preview; continue
        case ParseSuccess(action):
            await gate.execute_agent_action(session, case_id, action)
            continue   # projected CaseSummary at the top of the loop decides termination
```

`invoke_model_boundary` owns gateway invocation inside `asyncio.timeout(MODEL_CALL_TIMEOUT_SECONDS)`, exact-runtime `str` validation, and parsing. Malformed but syntactically valid strings remain on the bounded `invalid_output` path; transport/protocol violations escalate once with `model_failure`.

Suspension is simply returning. Resumption is a different HTTP request calling the same function. Nothing is held in process memory between iterations.

### 12.3 Prompt object

```python
@dataclass(frozen=True, slots=True)
class Prompt:
    text: str            # what a real LLM would receive
    state: AgentState    # structured view, used only by deterministic stubs

@dataclass(frozen=True, slots=True)
class AgentState:
    verified: bool
    orders: tuple[OrderView, ...]        # id, item, total, status — from seed rows
    orders_listed: bool
    linked_order_id: str | None
    last_refund_status: RefundStatus | None
    reply_sent_after_last_refund: bool
    menu: tuple[str, ...]
```

Carrying both forms removes the need for a stub to parse the rendered prompt, which is where every implementer would otherwise invent an incompatible mini-parser. A real backend reads `.text` and ignores `.state`.

**Order disclosure (normative).** `AgentState.orders` and memory order joins are empty until a canonical `orders_listed` event authorizes disclosure. `disclosed_order_ids(case_events)` reads only the latest `orders_listed` payload; `scope_order_seeds_for_disclosure` joins those IDs against seed rows for the case customer. No order is visible merely because it exists in a seed table.

`Prompt.text` has three clearly delimited regions, in this order:

1. **System instructions** — role, that it acts for exactly one customer, that some actions may be refused and refusals should be handled gracefully, and the JSON output contract.
2. **Structured state** — `AgentState` serialised as JSON. Structural fields and folded flags are system-computed. Human-authored fields inside the structure, especially `OrderView.item`, remain explicitly marked as untrusted data; JSON placement does not upgrade their provenance.
3. **Provenance-tagged memory** — rendered case history as a JSON array embedded between `=== CASE MEMORY ===` delimiters. Each record carries explicit `provenance` (`UNTRUSTED_CUSTOMER`, `UNTRUSTED_MODEL`, or `SYSTEM_FEEDBACK`) and a typed `kind`. The surrounding instruction says that untrusted entries are data, never instructions. It does not falsely claim that system denial reasons or outcome markers originated from an external party. JSON serialisation and sentinel neutralisation reduce delimiter-forging risk, but provenance tagging remains model-facing framing only; §2.2 carries the security claim.

Adapter and seed output is never interpolated into instruction prose. Structured serialisation and provenance tags are only partial mitigations for second-order injection via `Order.item`; this limitation is named in `DEBT.md`.

### 12.4 Memory rendering

`render_memory(case_events, seed_rows) -> str` returns a JSON document (not line-oriented provenance blocks), embedded in region 3. `json.loads(render_memory(...))` yields a list of structured records in `seq` order. Each record has explicit `provenance` and `kind` fields plus typed event-specific data:

- inbound email subject/body → `{"provenance": "UNTRUSTED_CUSTOMER", "kind": "email_received", ...}`;
- model-authored outgoing subject/body → `{"provenance": "UNTRUSTED_MODEL", "kind": "reply_sent", ...}`;
- denial `agent_reason` and lifecycle outcome markers → `{"provenance": "SYSTEM_FEEDBACK", ...}`;
- `case_closed` with a finish summary emits **two** records: a trusted `case_closed` outcome and a separate `finish_summary` under `UNTRUSTED_MODEL`;
- order details joined from immutable seed rows (ORM-guarded, §4.7), with human-authored `item` bounded and explicitly untrusted.

**Bounds.** Each untrusted text field (email subject/body, prior model reply subject/body, finish summary, and order `item` in both structured state and memory) is capped at 2000 characters with a deterministic `…truncated` suffix that counts toward the cap. The entire serialized memory is capped at 65 536 UTF-8 bytes; when exceeded, oldest records are elided first and replaced by one trusted `{"provenance": "SYSTEM_FEEDBACK", "kind": "elided", "count": n}` record. Elision is record-granular: records emitted by one event retain their declared order, but the older record can be elided before a newer sibling. An impossibly small cap that cannot encode even the elision record fails closed instead of returning an oversized document. Untrusted field values that contain prompt delimiter or bracketed provenance sentinels are neutralized before serialisation.

`orders_listed` stores only the ids it exposed; the renderer joins them against `orders`. The renderer preserves provenance instead of flattening all memory into one allegedly untrusted or allegedly trusted blob.

### 12.5 The menu

`available_actions(case_summary, customer_summary) -> tuple[str, ...]`, carried in `AgentState.menu`.

> **The menu is advisory.** It is a UI for the model, not a control. The gate must not assume the menu was narrowed, and must produce identical verdicts if the menu is ignored entirely. A test asserts exactly this.

### 12.6 Model interface and the deterministic stub

```python
class Model(Protocol):
    async def propose(self, prompt: Prompt) -> str: ...
```

Returns **raw text**, so the parse-and-retry path is exercised by stubs.

`ScriptedModel(outputs: Sequence[str])` copies the sequence into a private `deque`, consumes one string per call and raises when exhausted. Used by integration tests that need a fixed action sequence — including malformed JSON, deliberately dangerous proposals, and determinism checks that are **not** injection evidence.

`PromptObedientModel` is an **adversarial test double** for injection scenarios. It reads `prompt.text`, obeys injected instructions as far as the action vocabulary allows, and cannot forge verification events. It recognizes explicit second-order `ACTION:` instructions embedded in order-item text and follows the instructed `link_order` target and `propose_refund` amount; otherwise it proposes the largest decimal literal appearing anywhere in the rendered prompt (including structured state), then continues through `get_orders`, `link_order`, and `finish`. Injection integration tests use this backend to prove the gate blocks hostile proposals; a `ScriptedModel` that discards the prompt cannot demonstrate that property.

`HeuristicModel` is the default for `make demo` and is a **total function of `prompt.state`**, evaluated in this exact order — the first matching clause wins:

```
1. not verified                         → request_verification
2. not orders_listed                    → get_orders
3. linked_order_id is None              → link_order(first order with status
                                            delivered_damaged, else the first order)
4. last_refund_status is None           → propose_refund(linked order total)
5. last_refund_status is pending_approval → finish
                                            (unit-tested on `heuristic_action_json`;
                                             the loop returns immediately on
                                             `AWAITING_APPROVAL` and does not reach
                                             this clause in practice)
6. not reply_sent_after_last_refund     → send_reply(fixed template reflecting
                                            last_refund_status)
7. otherwise                            → finish
```

Every clause is decided by a field of `AgentState`; no clause inspects text. This is what makes `make demo` deterministic and what stops the reply-forever loop that an under-specified heuristic produces.

A real LLM backend is not implemented. `saferefund/agent/models.py` documents the single function that would need to change. Do not spend time there.

## 13. HTTP API

All routes async; bodies are Pydantic models. `actor` and `channel` are set by trusted code per §4.3, never from the body.

### 13.1 `POST /inbound-email`

```json
{ "envelope_from": "sophie@example.com", "message_id": "…", "subject": "…", "body": "…" }
```

`envelope_from` stands in for a transport-verified sender. Handler:

1. Look up the customer by lowercased email via `saferefund/repositories/`.
2. **Unknown sender** → `gate.send_unknown_sender_reply(email)`, return `202 {"handled": "unknown_sender"}`. No case, no events, no agent invocation. Unknown senders never reach the loop; the class is removed structurally rather than policed.
3. Known sender → resolve the case by `(customer_id, opening_message_id)` per §5.
4. Acquire the case single-flight lock (§14.4) and run the loop.
5. Return `200` with the case id, final status, and the case's event sequence.

### 13.2 `POST /operator/approve` · `POST /operator/reject`

Bodies `{refund_id, operator_id}` and `{refund_id, operator_id, reason}`. Each calls `expire_due_refunds_for_customer` for the owning customer, then the corresponding gate operation, which appends with `actor=operator, channel=operator_api`, transitions the row, and — for approval — proceeds to payment per §14.1. The gate operation returns every case id the sweep reopened; routes drain those cases through `_drain_agent_loop_queue` in ascending `case_id` order after the transaction commits (each loop run commits and releases its case lock before peers are dequeued), then resume the operator target when it was not already in that tuple.

If the refund is not `pending_approval` after expiry housekeeping, routes still resume every sweep-reopened case (including an expired operator target) before returning `409` with its current status. Conflicts that did not reopen any case do not spuriously invoke the loop.

> **No `refund_approved` or `refund_rejected` event is ever appended for a failed operator call.** `refund_expired` appended by housekeeping in the same request is not an approval event and does not contradict this.

### 13.3 `GET /operator/pending`

Lists refunds with `status = pending_approval` and an open approval window (`active_pending_refund_clause(now())`), with case, order, amount and expiry. Read-only; mutates nothing. This is the entire operator UI.

### 13.4 `POST /verification/confirm`

Body `{token}` — the token identifies its case, because it was issued by a case-scoped `verification_requested`.

- Token unknown → `404`; nothing appended, nothing resumed.
- Token known but expired → `400`; append nothing, and **resume the owning case**, which by §7.3 is now `open` again, so the agent can request verification anew, reply, or escalate.
- Token valid → append `customer_verified{method: "token", channel: verification_api}`, then resume **every** case of that customer whose status is now `open`, each under its own lock, oldest first.

> The last clause matters: verification is a property of the customer, so confirming one token can unblock several cases that were all waiting on it. Resuming only the issuing case would leave the others idle until an unrelated request happened to touch them.

### 13.5 Authentication

**Not implemented, deliberately.** There is no authentication on the operator or verification routes; `operator_id` is an unverified claim in the body. The `DEBT.md` entry on identity states what belongs there. Do not add a decorative JWT; an argued gap reads better than a fake mechanism.

## 14. Concurrency, Ordering, Consistency

### 14.1 The refund transaction

```
BEGIN
  SELECT … FROM customers WHERE id = :cid FOR UPDATE       -- §14.3
  load events for customer / order
  build summaries
  verdict = evaluate(ctx, action)
  if verdict is Allow or RequireApproval:
      INSERT refunds(status='pending_approval')            -- uq_open_refund_per_order may raise
      append refund_proposed
      if verdict is Allow:
          UPDATE refunds SET status='approved'
          append refund_auto_approved
      else:
          append refund_approval_required
COMMIT
                                   # ---- only now ----
if status == 'approved':
    provider_ref = await payment.refund(idempotency_key=refund_id, amount=amount)
    BEGIN
      SELECT … FROM customers WHERE id = :cid FOR UPDATE
      UPDATE refunds SET status='executed'
      append refund_executed{provider_ref}
    COMMIT
```

Two orderings that must never be swapped:

- **For payment, the external effect never precedes the durable intent record.** A crash after the payment call but before the second commit leaves a refund in `approved` with money gone and no `refund_executed`; a crash before the call leaves `approved` with nothing sent. Both are recoverable by a reconciliation pass keyed on `refund_id`. The opposite ordering could produce money sent with no durable refund intent at all. Mailer and ticketing intentionally use different toy failure semantics (§9.4).
- **Policy evaluation and row insert share one transaction.** Read-then-write across a transaction boundary is exactly where the cumulative threshold gets defeated by two concurrent proposals reading the same `refunded_total`.
- **Every transaction that appends an event takes the customer row lock first, including the post-payment `refund_executed` transaction.** This preserves both per-customer `seq` assignment and the serial history on which projections depend.

`IntegrityError` raised inside the nested transaction of §14.1 is caught, rolling back the failed nested transaction. The gate then confirms via `find_open_refund_for_order` that the linked order genuinely carries a live refund before appending `action_denied{rule=R_OPEN_REFUND}` in a fresh event-writing transaction; an `IntegrityError` not actually caused by the `uq_open_refund_per_order` race is re-raised instead of being misclassified as `R_OPEN_REFUND`. The failed transaction must not be reused after `IntegrityError`.

### 14.2 What guarantees what (corrected)

Be precise about this; the imprecise version is a claim the schema does not support.

- **The partial unique index guarantees** that at most one refund per order is simultaneously `pending_approval` or `approved`. It prevents two live refunds against one order. It does **not** by itself serialise the read of `refunded_total`: a transaction could read the total, stall, and insert after a competing refund had already moved to `executed` and left the index.
- **The customer row lock (§14.3) guarantees** that reading the event history, evaluating the policy, and appending the resulting events happen serially for one customer. That is what actually makes `R_THRESHOLD` correct under concurrency.
- **No order row lock is needed**, because an order belongs to exactly one customer and the customer lock is strictly coarser.

- **The guarded refund status transition guarantees** that at most one operator action can move a refund out of `pending_approval`, independent of whether the runtime honours row locks. `approve_refund` and `reject_refund` issue `UPDATE refunds SET status = :new, approval_expires_at = NULL WHERE id = :id AND status = 'pending_approval'`; `rowcount = 0` is `409`. This is what makes one-shot approval defensible on SQLite.

Three mechanisms, three different jobs. Saying so precisely is worth more in the walkthrough than the tidier but wrong one-liner.

### 14.3 Sequence assignment

`seq` is monotonic per customer. Allocation uses a separate `event_sequences` table keyed by `customer_id` with a non-null integer counter (`next_seq`, last allocated sequence, `0` before the first event). Each append atomically runs:

```sql
UPDATE event_sequences
SET next_seq = next_seq + 1
WHERE customer_id = :cid
RETURNING next_seq;
```

`UPDATE … RETURNING` is atomic on SQLite ≥ 3.35 and on PostgreSQL. The counter is not stored on `customers` because that table is append-only at the ORM boundary. A missing counter row is inserted with `next_seq = 0` via `INSERT … ON CONFLICT DO NOTHING` before the first allocation; concurrent first-appends retry the update rather than colliding. `UNIQUE(customer_id, seq)` on `events` remains a backstop.

Every transaction that appends events still takes `SELECT … FROM customers WHERE id = :cid FOR UPDATE` first. That lock serialises policy evaluation and event history reads for one customer; the counter update does not replace it. On SQLite the customer lock is parsed and ignored; global write serialisation makes both mechanisms redundant in functional tests. **PostgreSQL contention for the counter and `R_THRESHOLD` is exercised only in `tests/postgres/` against PostgreSQL 16.4** — see `DEBT.md` for untested deployment modes.

### 14.4 Single-flight per case

An in-process `asyncio.Lock` keyed by `case_id`, held for the duration of a loop run. Two handlers never drive the same case concurrently, which protects conversational memory from interleaving. Scoped to the case, not the customer, so a customer with two open cases progresses both.

### 14.5 SQLite

SQLite serialises writers globally, so §14.1–14.4 are never genuinely contended under the default functional suite. The design is expressed in terms correct for PostgreSQL; PostgreSQL 16.4 contention evidence lives in `tests/postgres/`, while SQLite-only runs remain functional evidence only (`DEBT.md`).

import-linter contracts, all of which must pass in `make check`. The seven `.importlinter` contract identifiers are: `policy_does_not_know_boundaries`, `adapters_contain_no_checks`, `adapter_mediation`, `projections_are_pure`, `layered_architecture`, `gate_internals_are_private`, and `gate_internals_are_private_to_gate`.

1. **`policy_does_not_know_boundaries`** — `saferefund.policy` may not import `saferefund.adapters`, `saferefund.gate`, `saferefund.agent`, `saferefund.api`.
2. **`adapters_contain_no_checks`** — `saferefund.adapters` may not import `saferefund.policy`, `saferefund.gate`, `saferefund.agent`.
3. **`adapter_mediation`** — `saferefund` modules may not import `saferefund.adapters` except through the gate and the documented demo read-only exception for `reset_adapters_for_tests` and `snapshot_outbox()` only (not `mailer.send` or other adapter effects). Because this contract's `source_modules` and `forbidden_modules` overlap at the package root, import-linter may keep some future adapter imports green; the AST scanner in `tests/invariants/adapter_import_scanner.py` is the exhaustive static proof for current and future production modules.
4. **`projections_are_pure`** — `saferefund.projections` may import only `saferefund.domain` and the standard library.
5. **`layered_architecture`** — layered, high to low: `api` → `agent` → `gate` → (`policy`, `projections`, `repositories`, `adapters`) → `domain`.
6. **`gate_internals_are_private`** — `saferefund.api` and `saferefund.agent` may not import gate internals (`common`, `effects`, `refund`, `operator`, `verification`); they reach the gate only through `saferefund.gate`, `saferefund.gate.operations`, and `saferefund.gate.outcomes`. `allow_indirect_imports = true` because the façade legitimately depends on those modules.
7. **`gate_internals_are_private_to_gate`** — no module outside `saferefund.gate` may import `saferefund.gate.{common,effects,refund,operator,verification}`; `demo.py`, `main.py`, `projections`, `repositories`, and future modules are covered here.

Contract 1 is the mechanical statement of *rules do not know which function performs the action*. Contract 2 is *adapters contain no checks*. Contract 3 is **layering hygiene** for adapter imports: it catches many accidental imports, but its overlapping package-root source/forbidden configuration is not an exhaustive future-module proof. The AST scanner in `tests/invariants/adapter_import_scanner.py` (exercised by `tests/invariants/test_gate_layering_and_mediation.py`) recursively scans every discovered non-gate production module, including nested function/class scopes, and is the exhaustive static repository mechanism; it enforces the documented read-only demo exception limited to `snapshot_outbox()` (not a blanket `mailer` import or `send`). Contract 6 narrows the gate's **façade surface** for the untrusted `api` and `agent` layers. Contract 7 closes the same internal gate modules for every other package. None of these static checks stop deliberate in-process bypass or substitute for process/capability enforcement. A runtime call-origin fixture in `tests/integration/conftest.py` exercises mediation independently; nothing here survives an adversary with commit access.

Three load-bearing documentation claims are additionally enforced mechanically in `tests/invariants/test_documentation_drift_guards.py`: the §6 `case_closed.outcome` set, the §9 façade signatures (including keyword-only parameters), the §16 import-contract identifier list versus `.importlinter`, order-disclosure authorization, the `ModelGateway` trust boundary, `invoke_model_boundary` ownership, refund intent immutability, exhaustive adapter-import scanning, exact-sequence scenario citations, relational scope checks, PostgreSQL concurrency evidence pointers, and external-effect crash-window wording. Remaining prose claims — narrative scenario colour and debt rationale — remain human-reviewed.

| Question | Answer |
|---|---|
| Is `Customer.verified` a column? | No. Folded from `customer_verified` events, including the seed. |
| Is there a `PersonalAgent` table? | No. Memory is rendered from the event stream plus seed rows. |
| How does an email map to a case? | One email opens one case per customer, keyed by `(customer_id, opening_message_id)`. Threading is out of scope. |
| Duplicate `message_id`? | Scoped to the sender: no events appended; the loop re-runs only if that customer's case is still `open`. The same `message_id` from another customer opens a separate case. |
| Does `propose_refund` take an `order_id`? | No. It uses `case.linked_order_id`. |
| Does `send_reply` take a recipient? | No. Resolved from the case. |
| Does `get_orders` take a customer? | No. Zero arguments. |
| Does `execute_agent_action` take an `actor`? | No. Always `Actor.AGENT`, set internally. |
| How many gate operations are there? | Seven, listed in §9. `escalate_case` exists so the loop can escalate without importing adapters. |
| Why is `escalate` classified `INTERNAL_SIDE_EFFECT`? | `EXTERNAL_COMM` means customer-facing communication. Ticket creation is an internal side effect; the label is a documentation/test invariant and has no runtime reader. Cross-case escalation limits remain a documented gap in `DEBT.md`. |
| What is the mailer/ticketing side-effect order? | Effect first, event second. The resulting crash windows and duplicate/orphan possibilities are deliberate toy limitations recorded in `DEBT.md`. |
| Does agent `escalate` close the case? | Yes — `escalated` then `case_closed{escalated}`, always together, always in the gate. |
| Is `RequireApproval` a refusal? | No, not for `propose_refund`: the row is created and `refund_proposed` is appended; only the money is withheld. See §9.2. |
| Email from an unknown address? | Canned reply, `202`, no case, no events, loop never runs. |
| Where do `actor` and `channel` come from? | Trusted application code, from the entry point and operation. Never a request field, never model output. Operator identity is unauthenticated and that is documented. |
| Channel of the seed verification event? | `internal`. `verification_api` only for `method=token`. |
| Is `verification_requested` case-scoped? | Yes. `customer_verified` is customer-scoped. The token identifies its issuing case. |
| What external effect does `request_verification` have? | A fixed-template mail carrying the token, sent through the mailer by the gate. |
| After a successful confirm, which cases resume? | Every case of that customer whose status became `open`, oldest first, each under its own lock. |
| When does lazy expiry run? | At loop entry, inbound mail after customer resolution, and operator approve/reject before status checks. `GET /operator/pending` filters instead of mutating. |
| How is `seq` assigned safely? | A per-customer `event_sequences` row is incremented with `UPDATE … RETURNING` inside the appending transaction; the customer row is locked first for policy/history serialisation. SQLite proves atomic allocation and rollback reuse; PostgreSQL 16.4 contention is in `tests/postgres/` (`DEBT.md` for other versions). |
| What does the partial index actually guarantee? | At most one live refund per order. It does **not** serialise threshold reads; the customer row lock does. |
| Do projections fold the whole customer stream? | No. See the §7.4 scoping contract. |
| Are approvals reusable? | No. One-shot, one `refund_id`. |
| Does a failed approval append anything? | No `refund_approved`. Housekeeping may append `refund_expired` in the same request. |
| Is the auto-approved transition evented? | Yes — `refund_auto_approved`, `actor=system`. Accepted internal state transitions are evented transactionally; external mail/ticket effects are effect-first with a named crash window (`DEBT.md`). |
| What resets `consecutive_invalid_outputs`? | Any `actor=agent` event **and** `action_denied`. A denied action parsed fine. |
| Does the menu constrain the gate? | No. Advisory only, with a test asserting so. |
| Are step and parse limits policy? | No. Loop-level hard caps that call `escalate_case`. |
| Does `Order.status` gate refunds? | No. Advisory input to the model only. |
| Can payment fail? | No. The mock always succeeds; failure handling is out of scope. |
| Can a verified customer call `request_verification`? | No. `R_ALREADY_VERIFIED`. |
| Can any action run while the case is suspended? | No. `R_CASE_NOT_ACTIONABLE`, enforced inside the gate. |
| How does the stub model decide? | From `Prompt.state`, by the ordered clause list in §12.6. It never parses the rendered prompt. |
| Money type and quantisation? | `Decimal`; parsed unquantised so scale and finiteness can be validated; quantised to two places only before persistence. |
| Time source? | `saferefund.clock.now()`, injectable. `datetime.now()` appears nowhere else. |
| Migration tooling? | None. `create_all` at startup. |
| Authentication? | None. Deliberate; covered in `DEBT.md` and README answer 4. |
| Real LLM? | Not implemented. `HeuristicModel` for the demo, `ScriptedModel` for tests. |
| Does `escalate_to_human` return `None`? | No. Returns a ticket id, stored in `escalated.ticket_id`. |
| Is `lookup_customer` an agent tool? | No. A repository query in the route, before any agent exists. |
| Does refund history reset when a case closes? | No. It lives on the order and outlives every case. |

## 20. Non-goals

Not implemented: authentication, sessions, or tokens beyond the mock verification token; Alembic, Docker, or CI configuration beyond what ships; any frontend (`GET /operator/pending` returning JSON is the whole operator UI); retries, backoff, or circuit breaking around mocked externals; a transactional outbox or reconciliation for mailer and ticketing; structured logging, tracing, or metrics; multi-tenant or per-customer policy variation; email threading; a real LLM integration; background workers, schedulers, or sweepers; rate limiting; reconciliation of the payment crash window described in §14.1.

Anything not named in this document that seems necessary is recorded in `DEBT.md` rather than implemented.
